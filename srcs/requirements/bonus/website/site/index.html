Docker Fundamentals

Master Docker concepts from the ground up — with real analogies and connections to this project.

🐳

What is Docker?

💡 Analogy

Imagine you're shipping goods internationally. Instead of worrying about how each item is stored differently on each truck, ship, and train — you put everything in a standardized container. The container is the same everywhere, so any transport system can handle it.

Docker does the same for software. Your application goes into a container that runs identically on any machine.

🔧 Technical

Docker is a platform that uses Linux kernel features (namespaces, cgroups, union filesystems) to create isolated environments called containers. Unlike virtual machines, containers share the host's kernel, making them lightweight and fast.

📦 In This Project

This Inception project uses Docker to run 7 isolated services: Nginx, WordPress, MariaDB, Redis, Adminer, FTP, and DNS — all on a single machine, each in its own container, communicating over a virtual network.

📦

Container

💡 Analogy

A container is like a private workspace in an office building. You have your own desk, your own supplies, your own phone line. You can't see or interfere with other people's workspaces, even though you share the same building (the host OS kernel).

🔧 Technical

A container is a running instance of an image. It's an isolated process (or group of processes) with its own filesystem, network, and process tree — created using Linux namespaces and cgroups. It shares the host kernel but has its own userspace.

📦 In This Project

Each service runs in its own container: nginx, wordpress, mariadb, redis, adminer, ftp, and dns. Each container has its own filesystem, network interfaces, and runs independently.

💿

Image

💡 Analogy

If a container is a running workspace, then an image is the blueprint used to build that workspace. It specifies what desk, what supplies, what software — everything needed. You can create many identical workspaces from the same blueprint.

🔧 Technical

A Docker image is a read-only template composed of layered filesystems. Each layer represents a Dockerfile instruction. Images are stored and shared via registries. When you run an image, Docker adds a writable layer on top, creating a container.

📦 In This Project

All containers are built from debian:bookworm-slim as the base image. Each Dockerfile adds specific packages on top: nginx, PHP-FPM, MariaDB server, Redis, vsftpd, dnsmasq, etc.

📝

Dockerfile

💡 Analogy

A Dockerfile is like a recipe card. It lists step-by-step instructions: "Start with Debian, add Nginx, copy this config file, expose port 443, run this command." Anyone with this recipe can reproduce the exact same result.

🔧 Technical

A text file with instructions (FROM, RUN, COPY, EXPOSE, CMD, ENTRYPOINT) that Docker executes sequentially to build an image. Each instruction creates a new layer in the image's union filesystem.

📦 In This Project

This project has 7 Dockerfiles, one per service. For example, the Nginx Dockerfile installs nginx and openssl, generates a self-signed TLS certificate, and copies the server configuration.

🎼

Docker Compose

💡 Analogy

Docker Compose is like an orchestra conductor's score. Instead of starting each musician individually, the conductor reads the score and coordinates the whole orchestra — which instruments play, when they start, how they interact.

🔧 Technical

A YAML file (docker-compose.yml) that defines multi-container applications. It specifies services, networks, volumes, secrets, environment variables, dependencies, and build contexts. docker compose up starts everything in the right order.

📦 In This Project

The docker-compose.yml defines all 7 services, the inception-net bridge network, 2 named volumes, 4 Docker secrets, and specifies dependencies (e.g., WordPress depends on MariaDB and Redis).

🌐

Networks

💡 Analogy

Docker networks are like private intercom systems in a building. Containers on the same network can call each other by name. Containers on different networks can't hear each other at all.

🔧 Technical

Docker creates virtual networks using Linux network namespaces and virtual Ethernet pairs (veth). A bridge network connects containers through a software bridge. Docker provides built-in DNS so containers can resolve each other's names.

📦 In This Project

inception-net (bridge driver) connects 6 containers. The DNS container is isolated — it doesn't join inception-net and only binds port 53 to 127.0.0.1 on the host to intercept local DNS queries.

💾

Volumes

💡 Analogy

Containers are ephemeral — like writing on a whiteboard. When you erase it (destroy the container), everything is gone. A volume is like a filing cabinet next to the whiteboard. You store important documents there, and they persist even if the whiteboard is wiped clean.

🔧 Technical

Docker volumes are managed storage areas that exist outside a container's writable layer. They persist when containers are removed. They can be shared between containers. Docker supports named volumes, anonymous volumes, and bind mounts.

📦 In This Project

mariadb_data persists the database at /var/lib/mysql. wordpress_data persists WordPress files at /var/www/html. Both use bind mounts to /home/oualid/data/ on the host.

🚪

Ports

💡 Analogy

Ports are like doors in a building. Each container has its own doors numbered differently. Port mapping connects an outside door (host port) to an inside door (container port). Visitors enter through the host door and arrive at the right container room.

🔧 Technical

Port mapping uses iptables rules to forward traffic from a host port to a container port. -p 443:443 maps host port 443 to container port 443. Internal ports (like 9000) are accessible only to containers on the same network.

📦 In This Project

Nginx exposes 443:443 (HTTPS). FTP exposes 21:21 + 6000-6010:6000-6010. WordPress (:9000), MariaDB (:3306), Redis (:6379), and Adminer (:8080) are internal only.

⚙️

Environment Variables

💡 Analogy

Environment variables are like sticky notes on your desk with important settings: "Database host is mariadb", "Domain is oobbad.42.fr". The application reads these notes instead of hardcoding values.

🔧 Technical

Key-value pairs injected into a container's environment at runtime. Defined via env_file, environment, or .env. Accessible as $VARIABLE_NAME in scripts. Used for configuration that changes between deployments.

📦 In This Project

The .env file sets: DOMAIN_NAME=oobbad.42.fr, MYSQL_DATABASE=inception_db, DB_HOST=mariadb, REDIS_HS=redis, and more. Used by MariaDB, WordPress, and Redis containers.

🔐

Docker Secrets

💡 Analogy

While environment variables are like sticky notes visible on your desk, secrets are like documents in a locked safe. Only authorized containers can open the safe and read the documents. They're never visible in logs or environment listings.

🔧 Technical

Docker secrets are encrypted at rest and mounted as files in /run/secrets/ inside containers. They're defined in docker-compose.yml and stored in files on the host. Only services with explicit access can read them.

📦 In This Project

4 secrets are used: db_passwd and db_root_passwd for MariaDB, wp_credentials for WordPress admin/user passwords, and ftp_credentials for the FTP user. Scripts read them with cat /run/secrets/... or source.

🔄

Container Lifecycle

💡 Analogy

A container's lifecycle is like a rented office space: you create it (sign the lease), start it (move in and work), stop it (lock up for the night), and remove it (end the lease). The space can be restarted anytime, and your filing cabinet (volume) survives even if you leave.

🔧 Technical

States: Created → Running → Paused → Stopped → Removed. The main process (PID 1) determines the container's life — when it exits, the container stops. restart: on-failure automatically restarts crashed containers.

📦 In This Project

All containers use restart: on-failure. The Makefile manages the lifecycle: make up builds and starts, make stop pauses, make down removes containers, make fclean removes everything including volumes and images.

🧱

Image Layers

💡 Analogy

Image layers are like transparent sheets stacked on top of each other. The bottom sheet is the base OS. Each new sheet adds something: one adds Nginx, another copies a config file. When viewed together, they form a complete picture.

🔧 Technical

Each Dockerfile instruction creates a read-only layer. Layers are cached and shared between images. If two images both FROM debian:bookworm-slim, they share that base layer. A union filesystem (OverlayFS) merges all layers into a single view.

📦 In This Project

All 7 services share the debian:bookworm-slim base layer, saving disk space. Each Dockerfile's RUN, COPY, and WORKDIR instructions add new layers on top of that shared base.

📡

Service Communication

💡 Analogy

Containers on the same Docker network can call each other by name, like coworkers in the same office using an internal phone directory. You dial "mariadb" and you reach the MariaDB container, no IP address needed.

🔧 Technical

Docker's embedded DNS server (at 127.0.0.11) resolves container names to their IP addresses within a user-defined network. This enables service discovery without hardcoded IPs. Containers communicate via TCP/UDP on their exposed internal ports.

📦 In This Project

Nginx connects to wordpress:9000 and adminer:8080 via FastCGI. WordPress connects to mariadb for database and redis for caching — all by container name, resolved by Docker DNS on the inception-net network.

N

Nginx

Reverse Proxy & SSL Termination
Mandatory

Nginx is the entry gate to the infrastructure. It listens on port 443 with a self-signed TLS certificate and routes incoming HTTPS requests to the appropriate backend service via FastCGI.

Configuration

Port: 443 (HTTPS) TLS: v1.2 & v1.3 RSA 4096-bit cert Network: inception-net

Dockerfile 

FROM debian:bookworm-slim
RUN apt-get update && apt-get install -y nginx openssl && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/* && \
    rm -rf /etc/nginx/sites-enabled/*

RUN mkdir -p /etc/nginx/certs && \
    openssl req -x509 -nodes -days 365 -newkey rsa:4096 \
        -keyout /etc/nginx/certs/server.key \
        -out /etc/nginx/certs/server.crt \
        -subj "/C=MA/ST=Rabat-sale/L=Rabat/O=UM6P-1337/OU=1337-cluster-1/CN=oobbad.42.fr"

COPY config/nginx.conf /etc/nginx/sites-enabled/

EXPOSE 443

CMD ["nginx", "-g", "daemon off;"]

Nginx Configuration 

server {
    listen 443 ssl;
    server_name oobbad.42.fr;
    ssl_certificate /etc/nginx/certs/server.crt;
    ssl_certificate_key /etc/nginx/certs/server.key;
    ssl_protocols TLSv1.2 TLSv1.3;
    root /var/www/html;
    index index.php index.html;

    location / {
        try_files $uri $uri/ /index.php?$args;
    }
    
    location ~ \.php$ {
        fastcgi_pass wordpress:9000;
        include fastcgi.conf;
    }

    location /adminer {
        include fastcgi_params;
        fastcgi_pass adminer:8080;
        fastcgi_param SCRIPT_FILENAME /var/www/html/adminer/adminer.php;
    }
}

Volumes

wordpress_data → /var/www/html — serves WordPress static files (CSS, JS, images)

Dependencies

Depends on: wordpress, adminer, dns

⚠️ If Removed

No HTTPS access. No TLS encryption. WordPress and Adminer become completely unreachable from outside the Docker network. The entire website goes down.

W

WordPress

PHP-FPM Application Server
Mandatory

WordPress runs on PHP-FPM 8.2, serving as the core web application. It handles dynamic content generation, communicates with MariaDB for data persistence and Redis for caching.

Configuration

Port: 9000 (FastCGI) PHP 8.2 FPM WP-CLI installed Network: inception-net

Dockerfile 

FROM debian:bookworm-slim

RUN apt-get update && apt-get install -y \
    php php-fpm php-mysql php-curl php-gd \
    php-mbstring php-xml php-zip php-opcache \
    php-redis curl tar mariadb-client \
    && rm -rf /var/lib/apt/lists/*

RUN curl -fsSL https://raw.githubusercontent.com/wp-cli/builds/gh-pages/phar/wp-cli.phar \
    -o /usr/local/bin/wp \
    && chmod +x /usr/local/bin/wp

RUN sed -i 's/^listen = .*/listen = 0.0.0.0:9000/' \
    /etc/php/8.2/fpm/pool.d/www.conf

WORKDIR /var/www/html
COPY tools/wordpress.sh /usr/local/bin/wordpress.sh
RUN chmod +x /usr/local/bin/wordpress.sh
CMD ["/usr/local/bin/wordpress.sh"]

Startup Process

  1. Source secrets from /run/secrets/wp_credentials
  2. Validate all required variables are present
  3. Download WordPress if index.php doesn't exist
  4. MariaDB is guaranteed ready (Docker Compose healthcheck + condition: service_healthy)
  5. Create wp-config.php via wp config create
  6. Install WordPress core with wp core install
  7. Create a second user with author role
  8. Install and activate Redis cache plugin
  9. Set ownership to www-data
  10. Start php-fpm8.2 -F (foreground mode)

Volumes

wordpress_data → /var/www/html — stores WordPress files, themes, plugins, uploads

Dependencies

Depends on: mariadb, redis

⚠️ If Removed

No web application. Nginx returns 502 Bad Gateway for all requests. The entire site is non-functional.

M

MariaDB

Database Server
Mandatory

MariaDB stores all WordPress data: posts, pages, users, settings, and plugin data. It's the persistent data backbone of the application.

Configuration

Port: 3306 (MySQL) bind-address: 0.0.0.0 DB: inception_db Network: inception-net

Dockerfile 

FROM debian:bookworm-slim
RUN apt-get update && \
    apt-get install -y --no-install-recommends \
        mariadb-server mariadb-client \
    && apt-get clean \
    && rm -rf /var/lib/apt/lists/* \
    && rm -rf /var/lib/mysql
RUN mkdir -p /run/mysqld /var/lib/mysql && \
    chown -R mysql:mysql /run/mysqld /var/lib/mysql
COPY tools/mariadb.sh tools/
RUN chmod +x tools/mariadb.sh
ENTRYPOINT [ "tools/mariadb.sh" ]
CMD ["mariadbd", "--user=mysql", "--bind-address=0.0.0.0"]

Startup Process

  1. Read root password from /run/secrets/db_root_passwd
  2. Read user password from /run/secrets/db_passwd
  3. Validate all variables are present
  4. If first boot: run mariadb-install-db --user=mysql
  5. Start temporary MariaDB server in background
  6. Wait for it to be ready (up to 30 attempts)
  7. Set root password, create database, create user, grant privileges
  8. Shutdown temporary server
  9. Exec mariadbd --user=mysql --bind-address=0.0.0.0

Volumes

mariadb_data → /var/lib/mysql — stores all database files, tables, indices

Secrets

db_passwd, db_root_passwd

⚠️ If Removed

WordPress cannot store or retrieve any data. All content, users, and settings are inaccessible. The site fails to load entirely.

R

Redis

Object Cache Server
Bonus

Redis provides in-memory caching for WordPress. It stores frequently accessed data (rendered pages, database queries) to reduce MariaDB load and speed up responses.

Configuration

Port: 6379 (Redis) bind: 0.0.0.0 protected-mode: no Network: inception-net

Dockerfile 

FROM debian:bookworm-slim

RUN apt-get update && \
    apt-get install -y lsb-release curl gpg && \
    curl -fsSL https://packages.redis.io/gpg | \
    gpg --dearmor -o /usr/share/keyrings/redis-archive-keyring.gpg && \
    chmod 644 /usr/share/keyrings/redis-archive-keyring.gpg && \
    echo "deb [signed-by=/usr/share/keyrings/redis-archive-keyring.gpg] \
    https://packages.redis.io/deb $(lsb_release -cs) main" | \
    tee /etc/apt/sources.list.d/redis.list && \
    apt-get update && \
    apt-get install -y redis-server && \
    apt-get clean && rm -rf /var/lib/apt/lists/*

RUN sed -i 's/^bind 127.0.0.1 -::1/bind 0.0.0.0/' /etc/redis/redis.conf
RUN sed -i 's/^protected-mode yes/protected-mode no/' /etc/redis/redis.conf

CMD ["redis-server", "/etc/redis/redis.conf"]

WordPress Integration

The wordpress.sh script installs the redis-cache plugin and configures WP_REDIS_HOST=redis on port 6379. Object cache is stored in /wp-content/object-cache.php.

⚠️ If Removed

WordPress still works, but slower. Every page load hits MariaDB directly. No caching layer means higher database load and slower response times.

Database Management UI
Bonus

Adminer is a lightweight, single-file PHP database management tool. It provides a web interface to inspect and manage the MariaDB database — like phpMyAdmin but much simpler.

D

DNS

Local Domain Resolver
Bonus

Runs dnsmasq to resolve oobbad.42.fr to the host machine's IP. Enables the .42.fr domain to work locally without modifying /etc/hosts.

Configuration

Port: 127.0.0.1:53 (DNS) dnsmasq ⚠️ Not on inception-net

dnsmasq.conf 

listen-address=0.0.0.0
bind-interfaces
address=/oobbad.42.fr/127.0.0.1
server=8.8.8.8
server=1.1.1.1

How It Works

The Makefile locks /etc/resolv.conf to point to this container (using chattr +i). All DNS queries go through dnsmasq. Queries for oobbad.42.fr resolve locally; all other queries are forwarded to Google (8.8.8.8) and Cloudflare (1.1.1.1).

⚠️ If Removed

oobbad.42.fr won't resolve. You must manually add entries to /etc/hosts. The Makefile DNS locking mechanism would break.

Configuration

Docker Compose Explained

A walkthrough of the actual docker-compose.yml — what each directive does and why.

Networks

networks:
  inception-net:
    driver: bridge

Defines a single bridge network called inception-net. This creates an isolated virtual network where containers can communicate using their names as hostnames. Docker's embedded DNS automatically resolves mariadb, wordpress, redis, etc. to their container IPs.

The bridge driver is Docker's default — it creates a software bridge on the host that containers connect to via virtual Ethernet pairs (veth interfaces).

Volumes

volumes:
  mariadb_data:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /home/${LOGIN}/data/mariadb
  wordpress_data:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /home/${LOGIN}/data/wordpress

Two named volumes with bind mount behavior. The driver_opts trick uses the local driver with type: none and o: bind to mount specific host directories.

Why not regular bind mounts? Named volumes appear in docker volume ls and can be managed with Docker commands. The ${LOGIN} variable (set to oualid) makes the paths portable.

mariadb_data persists the database at /home/oualid/data/mariadb. wordpress_data persists WordPress files at /home/oualid/data/wordpress.

Secrets

secrets:
  db_passwd:
    file: ../secrets/db_password.txt
  db_root_passwd:
    file: ../secrets/db_root_password.txt
  wp_credentials:
    file: ../secrets/wp_credentials.txt
  ftp_credentials:
    file: ../secrets/ftp_credentials.txt

Docker secrets store sensitive data (passwords, credentials) securely. They're mounted as read-only files at /run/secrets/<name> inside containers — never exposed as environment variables, never visible in logs or docker inspect.

Each secret file is in the ../secrets/ directory (outside the srcs/ directory). Only containers that explicitly list a secret in their secrets: key can access it.

Services — MariaDB

  mariadb:
    container_name: mariadb
    build: ./requirements/mariadb
    networks:
      - inception-net
    volumes:
      - mariadb_data:/var/lib/mysql
    env_file:
      - .env
    secrets:
      - db_passwd
      - db_root_passwd
    healthcheck:
      test: ["CMD", "mariadb-admin", "ping", "-h", "localhost"]
      interval: 2s
      timeout: 3s
      retries: 10
    restart: on-failure

build points to the directory containing the Dockerfile. container_name sets a fixed name (also used as DNS hostname). env_file loads environment variables from .env. restart: on-failure restarts the container if it crashes (but not if stopped manually).

The healthcheck runs mariadb-admin ping every 2 seconds. Other services use depends_on: condition: service_healthy to wait until MariaDB is actually accepting connections — not just until the container starts.

No depends_on — MariaDB is the foundation that other services wait for.

Services — WordPress

  wordpress:
    container_name: wordpress
    build: ./requirements/wordpress
    networks:
      - inception-net
    volumes:
      - wordpress_data:/var/www/html
    env_file:
      - .env
    secrets:
      - wp_credentials
    depends_on:
      mariadb:
        condition: service_healthy
      redis:
        condition: service_started
    healthcheck:
      test: ["CMD", "test", "-f", "/var/www/html/wp-config.php"]
      interval: 2s
      timeout: 2s
      retries: 10
    restart: on-failure

depends_on with condition: service_healthy ensures MariaDB's healthcheck passes before WordPress starts. This eliminates the need for a polling loop inside wordpress.sh — Docker Compose handles the orchestration natively.

WordPress itself has a healthcheck that checks for wp-config.php. Services like FTP and Nginx use condition: service_healthy on WordPress to guarantee it's fully installed before they start.

The wordpress_data volume at /var/www/html is shared with Nginx (for serving static files) and FTP (for file uploads).

Services — Nginx

  nginx:
    container_name: nginx
    build: ./requirements/nginx
    networks:
      - inception-net
    volumes:
      - wordpress_data:/var/www/html
    ports:
      - "443:443"
    depends_on:
      wordpress:
        condition: service_healthy
      adminer:
        condition: service_started
      website:
        condition: service_started
    restart: on-failure

ports: "443:443" maps host port 443 to container port 443 — this is the only publicly accessible port for the main website. Nginx is the last service to start because it depends on everything it proxies to.

depends_on uses condition: service_healthy on WordPress to guarantee WordPress is fully installed (wp-config.php exists) before Nginx tries to proxy to it. Adminer and website only need service_started.

It mounts wordpress_data to serve static assets directly without going through PHP-FPM (the try_files directive checks the filesystem first).

Services — DNS (Isolated)

  dns:
    container_name: dns
    build: ./requirements/bonus/dns
    ports:
      - "127.0.0.1:53:53/udp"
      - "127.0.0.1:53:53/tcp"
    restart: on-failure

DNS is not on inception-net — it doesn't need to communicate with any other container. It only serves the host machine so that oobbad.42.fr resolves to 127.0.0.1.

Ports are bound to 127.0.0.1 only, keeping DNS strictly local. The Makefile configures /etc/resolv.conf to point to this container.

Bridge Network: inception-net

Six containers share the inception-net bridge network. Docker creates a virtual bridge (br-xxxxx) on the host and connects each container via a virtual Ethernet pair (veth). Containers on this network can reach each other by name using Docker's embedded DNS resolver at 127.0.0.11.

Host Network: DNS Container

The DNS container is not on inception-net. It binds port 53 to 127.0.0.1 only, so dnsmasq can intercept all DNS queries from the host machine. It resolves oobbad.42.fr to 127.0.0.1 (localhost) and forwards all other queries to Google (8.8.8.8) and Cloudflare (1.1.1.1).

Port Mapping

Only two services expose ports to the host: Nginx (443:443) and FTP (21:21, 6000-6010:6000-6010). All other services (WordPress:9000, MariaDB:3306, Redis:6379, Adminer:8080) are internal only — accessible only from within the Docker network.

FastCGI Protocol

Nginx communicates with WordPress and Adminer using the FastCGI protocol, not HTTP. FastCGI is a binary protocol optimized for forwarding requests to PHP-FPM. The fastcgi_pass directive in nginx.conf specifies the upstream server: wordpress:9000 for WordPress, adminer:8080 for Adminer.

Why Bind Mounts via Named Volumes?

This project uses a clever technique: named volumes with driver_opts that specify type: none and o: bind. This gives the benefits of both approaches — the volumes appear in docker volume ls and can be managed by Docker, while the data is stored at a known location on the host filesystem.

Shared Volume: wordpress_data

The wordpress_data volume is mounted by three containers: WordPress (reads/writes PHP files), Nginx (reads static assets to serve directly), and FTP (allows file uploads). This shared access is what enables the architecture to work — WordPress generates content, Nginx serves it, and FTP allows file management.

What Happens Without Volumes?

Without volumes, all data lives in the container's writable layer. Running docker compose down destroys the containers and all data is lost: database entries, WordPress posts, uploaded files — everything. Volumes ensure data survives container lifecycle events.

The Makefile's Data Management

The Makefile creates data directories with mkdir -p during make up and removes them with sudo rm -rf during make fclean. The clean target uses docker compose down -v to remove Docker volumes, while fclean additionally removes the host directories for a complete reset.

Data Flow

Request Flow

What happens when you visit https://oobbad.42.fr — step by step.

1

🌐 Browser Request

You type https://oobbad.42.fr in your browser. The browser needs to resolve this domain name to an IP address.

2

🔍 DNS Resolution

The OS checks /etc/resolv.conf, which points to 127.0.0.1 (the dnsmasq container). Dnsmasq matches oobbad.42.fr against its address= rule and returns 127.0.0.1. No external DNS query needed.

address=/oobbad.42.fr/127.0.0.1
3

🔒 TLS Handshake

The browser connects to port 443 on the resolved IP. Nginx presents its self-signed TLS certificate (RSA 4096-bit). The browser may warn about the self-signed cert. After accepting, a secure TLS 1.2 or 1.3 session is established.

4

📋 Nginx Routing

Nginx receives the HTTPS request and checks its location blocks. For PHP files, it matches location ~ \.php$ and forwards via FastCGI. For static files (CSS, JS, images), try_files serves them directly from the wordpress_data volume.

fastcgi_pass wordpress:9000;
5

⚡ PHP-FPM Processing

WordPress receives the request via FastCGI on port 9000. PHP-FPM spawns a worker process to execute the WordPress PHP code. WordPress first checks the Redis cache for a cached version of the requested page.

6

💨 Redis Cache Check

WordPress queries Redis at redis:6379 for cached data. On a cache hit, the cached response is returned immediately (skipping the database). On a cache miss, WordPress proceeds to query MariaDB.

7

🗄️ Database Query

WordPress connects to MariaDB at mariadb:3306 using the credentials from secrets. It queries the inception_db database for posts, pages, settings, and user data. Results are returned to PHP.

8

🏗️ Page Rendering

WordPress assembles the HTML page using the database results, applies the active theme, and stores the result in Redis cache for future requests. The rendered HTML is returned to Nginx via FastCGI.

9

📤 Response Delivery

Nginx receives the HTML from WordPress and sends it back to the browser over the TLS-encrypted connection. The browser renders the page, loading additional static assets (CSS, JS, images) which Nginx serves directly from the shared volume.

Scripts Explained

Line-by-line breakdown of the initialization scripts that make the containers work.

mariadb.sh

mariadb ENTRYPOINT script

This script initializes the MariaDB database on first boot. It reads passwords from Docker secrets, installs the system tables, creates the application database and user, then hands off to the actual MariaDB server process.

#!/bin/sh
set -e

#!/bin/sh — Use the POSIX shell (lightweight, available in all containers).

set -e — Exit immediately if any command fails. This is critical for initialization scripts — if any step fails, we don't want to continue with a broken setup.

if [ -f /run/secrets/db_root_passwd ]; then
    MYSQL_ROOT_PASSWORD=$(cat /run/secrets/db_root_passwd)
fi

if [ -f /run/secrets/db_passwd ]; then
    MYSQL_PASSWORD=$(cat /run/secrets/db_passwd)
fi

Reads passwords from Docker secrets. The -f flag checks if the file exists. cat reads the file content into a variable. This is more secure than passing passwords as environment variables, which would be visible in docker inspect.

if [ -z "$MYSQL_ROOT_PASSWORD" ] || [ -z "$MYSQL_DATABASE" ] || \
   [ -z "$MYSQL_USER" ] || [ -z "$MYSQL_PASSWORD" ]; then
    echo "[ERROR] ..." >&2
    exit 1
fi

-z checks if a variable is empty. This validation ensures all required variables are set before proceeding. >&2 sends the error message to stderr (standard error). exit 1 terminates with a non-zero status code (indicating failure).

if [ ! -d "/var/lib/mysql/mysql" ]; then
    mariadb-install-db --user=mysql --datadir=/var/lib/mysql > /dev/null

! -d checks if the mysql system database directory does not exist — meaning this is the first boot. mariadb-install-db creates the system tables (user accounts, privileges). --user=mysql ensures files are owned by the mysql user. Output is suppressed with > /dev/null.

On subsequent boots, this entire block is skipped because /var/lib/mysql/mysql already exists (persisted by the volume).

    mariadbd --user=mysql &
    pid="$!"

    while ! mysqladmin ping --silent; do
        counter=$((counter + 1))
        if [ "$counter" -ge "$max_attempts" ]; then
            echo "[ERROR] MariaDB failed to start" >&2
            kill -9 "$pid" 2>/dev/null || true
            exit 1
        fi
        sleep 1
    done

Starts a temporary MariaDB server in the background (&) and captures its PID ($!). Then polls with mysqladmin ping until the server is ready, with a 30-second timeout. If it fails to start, the script kills the process and exits.

Why a temporary server? We need a running server to execute SQL commands (create users, databases). After initialization, we shut it down and start the real server with exec.

    mysql -u root << EOF
ALTER USER 'root'@'localhost' IDENTIFIED BY '${MYSQL_ROOT_PASSWORD}';
CREATE DATABASE IF NOT EXISTS \`${MYSQL_DATABASE}\`;
CREATE USER IF NOT EXISTS '${MYSQL_USER}'@'%' IDENTIFIED BY '${MYSQL_PASSWORD}';
GRANT ALL PRIVILEGES ON \`${MYSQL_DATABASE}\`.* TO '${MYSQL_USER}'@'%';
FLUSH PRIVILEGES;
EOF

SQL commands executed via heredoc (<< EOF):

  • ALTER USER — Sets the root password (no password by default after install)
  • CREATE DATABASE — Creates inception_db
  • CREATE USER — Creates inception_user accessible from any host (@'%')
  • GRANT ALL — Gives the user full access to the database
  • FLUSH PRIVILEGES — Reloads the privilege tables

The backtick escapes (\`) protect database names with special characters.

    mysqladmin -u root -p"${MYSQL_ROOT_PASSWORD}" shutdown
    wait "$pid"
fi

exec "$@"

mysqladmin shutdown cleanly stops the temporary server. wait "$pid" ensures the process is fully terminated before continuing.

exec "$@" is the key pattern — it replaces the current shell process with the CMD from the Dockerfile: mariadbd --user=mysql --bind-address=0.0.0.0. This makes MariaDB PID 1 in the container, which is important for signal handling and container lifecycle.

wordpress.sh

wordpress CMD script

This script is the main entry point for the WordPress container. It handles credential loading, WordPress download, database connection waiting, WP-CLI configuration, Redis cache setup, and finally starts PHP-FPM.

#!/bin/bash
set -e

if [ ! -f /run/secrets/wp_credentials ]; then
    echo "[ERROR] wp_credentials is missing!" >&2
    exit 1
fi
source /run/secrets/wp_credentials

Uses bash (not sh) because source is a bash built-in. The wp_credentials secret file contains variable assignments like DB_PASSWORD=..., WP_ADMIN_PASSWORD=..., etc. The source command executes the file in the current shell, loading all variables into the environment.

if [ ! -f "$WP_DIR/index.php" ]; then
    rm -f "$WP_DIR/index.html"
    curl -fsSL https://wordpress.org/latest.tar.gz -o /tmp/wordpress.tar.gz
    tar -xzf /tmp/wordpress.tar.gz -C /tmp
    cp -a /tmp/wordpress/. "$WP_DIR/"
    rm -rf /tmp/wordpress /tmp/wordpress.tar.gz
fi

Downloads WordPress only if index.php doesn't exist (first boot). curl -fsSL downloads silently but fails on HTTP errors (-f). The tarball is extracted to /tmp first, then copied to /var/www/html. The -a flag preserves permissions. Temp files are cleaned up.

On subsequent boots, WordPress files already exist in the persistent volume, so this is skipped.

# No MariaDB wait loop needed!
# docker-compose.yml handles this:
#   depends_on:
#     mariadb:
#       condition: service_healthy

Unlike many Docker setups that use an until polling loop to wait for the database, this project uses Docker Compose healthchecks. MariaDB has a healthcheck that runs mariadb-admin ping, and WordPress uses depends_on: condition: service_healthy. Docker Compose won't start WordPress until MariaDB's healthcheck passes — making the wait loop unnecessary and the script cleaner.

if [ ! -f "$WP_DIR/wp-config.php" ]; then
    wp config create --path="$WP_DIR" \
        --dbname="$MYSQL_DATABASE" --dbuser="$MYSQL_USER" \
        --dbpass="$DB_PASSWORD" --dbhost="$DB_HOST" --allow-root
fi

if ! wp core is-installed --path="$WP_DIR" --allow-root; then
    wp core install --path="$WP_DIR" --url="$WP_URL" \
        --title="$WP_TITLE" --admin_user="$WP_ADMIN_USER" \
        --admin_password="$WP_ADMIN_PASSWORD" \
        --admin_email="$WP_ADMIN_EMAIL" --allow-root

    wp user create "$WP_USER" "$WP_USER_EMAIL" \
        --user_pass="$WP_USER_PASSWORD" --role=author \
        --path="$WP_DIR" --allow-root
fi

Each step is guarded by an if check to make the script idempotent — safe to run multiple times without duplicating work. wp config create only runs if wp-config.php doesn't exist. wp core install only runs if WordPress isn't already installed (checked by wp core is-installed). The second user is created inside the same block since it's part of the initial install. --allow-root is needed because the script runs as root inside the container.

if [ ! -f "$WP_DIR/wp-content/object-cache.php" ]; then
    wp config set WP_CACHE true --raw --allow-root --path="$WP_DIR"
    wp config set WP_REDIS_HOST "$REDIS_HS" --allow-root --path="$WP_DIR"
    wp config set WP_REDIS_PORT 6379 --raw --allow-root --path="$WP_DIR"
    wp plugin install redis-cache --activate --allow-root --path="$WP_DIR" --force
    wp redis enable --allow-root --path="$WP_DIR"
fi

chown -R www-data:www-data /var/www/html
exec php-fpm8.2 -F

Configures Redis caching only if object-cache.php doesn't exist (first boot). Sets WP_CACHE=true, configures the Redis host and port, installs and activates the redis-cache plugin, and enables the Redis object cache.

chown -R www-data:www-data ensures PHP-FPM can read/write all WordPress files. exec php-fpm8.2 -F replaces the shell with PHP-FPM in foreground mode (-F), making it PID 1.

ftp.sh

ftp ENTRYPOINT script

This script initializes the vsftpd FTP server. It creates an FTP user from secrets, sets file permissions, configures vsftpd for local user access with passive mode, and starts the server. WordPress is guaranteed ready via depends_on: condition: service_healthy.

#!/bin/bash

if [ ! -f /run/secrets/ftp_credentials ]; then
    echo "[ERROR] ftp_credentials is missing!" >&2
    exit 1
fi

source /run/secrets/ftp_credentials

if [ -z "$FTP_USER" ] || [ -z "$FTP_PWD" ]; then
    echo "[ERROR] One or more required variables are missing!" >&2
    exit 1
fi

if ! id "$FTP_USER" &>/dev/null; then
    adduser "$FTP_USER" --disabled-password --gecos ""
    echo "$FTP_USER:$FTP_PWD" | chpasswd
    usermod -aG 33 "$FTP_USER"
fi

First validates that the secrets file exists and all required variables are set — failing fast with clear error messages if anything is missing. Then creates the FTP user only if it doesn't already exist (id returns non-zero for non-existent users). --disabled-password prevents login via password (SSH), while chpasswd sets the FTP password. usermod -aG 33 adds the user to group 33 (www-data), enabling proper file permissions.

chown -R 33:33 /var/www/html
chmod -R g+w /var/www/html

Sets ownership to UID/GID 33 (www-data) and adds group write permissions. No wait loop is needed — Docker Compose's depends_on: wordpress: condition: service_healthy guarantees WordPress is fully installed (wp-config.php exists) before the FTP container starts. This ensures both PHP-FPM and the FTP user can read and write WordPress files.

if ! grep -q "#isconfigured" /etc/vsftpd.conf; then
    sed -i -r "s/#write_enable=YES/write_enable=YES/1" /etc/vsftpd.conf
    sed -i -r "s/#chroot_local_user=YES/chroot_local_user=YES/1" /etc/vsftpd.conf
    echo "
local_enable=YES
allow_writeable_chroot=YES
pasv_enable=YES
seccomp_sandbox=NO
local_root=/var/www/html
pasv_min_port=6000
pasv_max_port=6010
local_umask=0002
#isconfigured" >> /etc/vsftpd.conf
fi
mkdir -p /var/run/vsftpd/empty
exec "$@"

Configures vsftpd only once (checks for #isconfigured marker). Key settings:

  • write_enable=YES — Allows file uploads
  • chroot_local_user=YES — Jails users to their home directory
  • local_root=/var/www/html — FTP root is the WordPress directory
  • pasv_min/max_port=6000-6010 — Passive mode port range
  • seccomp_sandbox=NO — Disables seccomp (needed in containers)
  • local_umask=0002 — New files are group-writable

mkdir -p /var/run/vsftpd/empty creates vsftpd's required empty directory. exec "$@" starts vsftpd /etc/vsftpd.conf from the CMD.

Linux Namespaces

🏢

The Apartment Building Analogy

Imagine an apartment building. Everyone lives in the same physical building (the Linux kernel). Each apartment has its own door number, its own mailbox, its own utility meters, and its own interior. From inside your apartment, you mainly see your own private environment. You don't normally see inside other apartments, even though you all share the same building structure, foundation, and roof.

Linux namespaces work the same way — they create isolated views of system resources for each container, even though all containers share the same kernel.

PID

Process ID Namespace

Analogy: Each apartment has its own numbering for rooms. Apartment A calls its living room "Room 1", and Apartment B also calls its living room "Room 1" — the same number, different rooms.
What it isolates: Process IDs. Inside each container, the main process is PID 1 (like mariadbd or php-fpm8.2). Each container sees only its own processes, even though the host sees all processes across all containers with different PIDs.
In Docker: When mariadb.sh uses exec "$@", MariaDB becomes PID 1 inside its container. If PID 1 exits, the container stops. The host might see this process as PID 48291 — completely different numbers.
NET

Network Namespace

Analogy: Each apartment has its own phone line and internet connection. Apartment A's phone number is different from Apartment B's. They each have their own private network.
What it isolates: Network interfaces, IP addresses, routing tables, port numbers, and firewall rules. Each container gets its own network stack with its own eth0, its own IP address, and its own set of ports.
In Docker: Both WordPress and Adminer listen on different ports (9000 and 8080) on their own network interfaces. Docker connects them to the inception-net bridge via virtual Ethernet pairs. The DNS container is isolated from the bridge — it only binds to 127.0.0.1:53 on the host.
MNT

Mount Namespace

Analogy: Each apartment has its own furniture and storage, arranged differently. Apartment A might have a bookshelf where Apartment B has a desk. They share the building's structure but have completely different interiors.
What it isolates: Mount points — the filesystem tree. Each container sees its own root filesystem (from the image) and any mounted volumes, without seeing the host's files or other containers' files.
In Docker: MariaDB sees /var/lib/mysql as its database directory (mounted from mariadb_data). WordPress sees /var/www/html as its web root. Neither can access the other's files unless they share a volume (like wordpress_data shared by nginx, wordpress, and ftp).
UTS

UTS Namespace

Analogy: Each apartment has its own door nameplate. Apartment A might say "The Smiths", Apartment B might say "The Johnsons" — different names, same building.
What it isolates: The hostname and domain name. Each container can have its own hostname without affecting others. UTS stands for "UNIX Time-Sharing" (a historical term).
In Docker: The container_name directive sets the hostname. When you docker exec -it mariadb bash, the shell prompt shows root@mariadb. Docker's DNS resolves this hostname to the container's IP on the bridge network.
IPC

IPC Namespace

Analogy: Each apartment has its own internal intercom system and shared bulletin board. Messages left on Apartment A's bulletin board are invisible to Apartment B.
What it isolates: Inter-process communication resources: shared memory segments, message queues, and semaphores. Processes in one container cannot access IPC resources of another container.
In Docker: If MariaDB uses shared memory for internal communication between its threads, that shared memory is invisible to processes in the WordPress container. This prevents data leaks and interference between services.
USER

User Namespace

Analogy: Each apartment has its own "owner" and "tenant" roles. You might be the "owner" (root) inside your apartment, but you're just a regular resident of the building (unprivileged user on the host).
What it isolates: User and group IDs. A process can be UID 0 (root) inside the container but mapped to a non-root UID on the host. This adds a security layer — even if a container process escapes, it has limited host privileges.
In Docker: The MariaDB script reads secrets and starts the server as root inside the container, then the server runs as the mysql user. WordPress runs PHP-FPM as www-data. These are container-local users — the actual host UIDs may differ.

Linux Control Groups (cgroups)

🏗️

The Building Resource Manager Analogy

Imagine the apartment building has limited resources: a finite amount of electricity, water, and heating capacity. Without controls, one apartment could run all their appliances at maximum and consume everything, leaving other apartments without power.

The building manager installs individual meters and circuit breakers for each apartment. Each apartment gets a fair share of resources, and if one apartment tries to use too much electricity, its circuit breaker trips — protecting the rest of the building.

Linux cgroups work exactly the same way for containers — they limit and account for resource usage per container.

⚡

CPU Limits

Like an electricity allowance per apartment. You can limit how much CPU time a container gets. A container using too much CPU won't slow down other containers — the kernel's scheduler enforces the limit.

Example: Limit MariaDB to 2 CPU cores so it can't monopolize the processor during heavy queries.

🧠

Memory Limits

Like a water tank per apartment. Each container gets a maximum amount of RAM. If a container tries to use more than its limit, the kernel's OOM (Out-of-Memory) killer terminates it — preventing one runaway process from crashing the entire host.

Example: Limit Redis to 256MB so it doesn't consume all available RAM with cached data.

📋

Process Limits

Like a limit on how many people can live in each apartment. Controls the maximum number of processes a container can create, preventing fork bombs or runaway process creation.

Example: Limit WordPress to 100 processes to prevent a PHP-FPM misconfiguration from spawning unlimited workers.

📊

Resource Accounting

Like the building's utility meters. Cgroups track exactly how much CPU, memory, disk I/O, and network each container uses. This data is what docker stats reads to show you real-time resource usage per container.

Command: docker stats shows live CPU %, memory usage, network I/O, and block I/O for every running container.

Filesystem Isolation

OverlayFS — Union Filesystem

Docker uses OverlayFS to create the illusion that each container has its own complete filesystem. It works by layering:

  1. Lower layers (read-only) — The image layers from the Dockerfile (debian:bookworm-slim + packages + configs)
  2. Upper layer (writable) — The container's working layer where runtime changes are stored
  3. Merged view — What the container actually sees — a unified filesystem

When a container modifies a file from a lower layer, OverlayFS performs copy-on-write: it copies the file to the upper layer and modifies the copy, leaving the original image layer untouched. This is why multiple containers can share the same base image without interfering with each other.
